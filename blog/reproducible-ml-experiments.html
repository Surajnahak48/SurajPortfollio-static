Keeping experiments reproducible

August 10, 2026    Suraj Nahak

ReproducibilityExperimentsResearch

A few months after an experiment, someone asks how you got a particular result. You find the notebook, run it again, and get a different number. Not wildly different, just different enough that you can't say which one to trust.

That's happened to me enough times that reproducibility is now part of how I set up a project from day one. None of it takes long, and it all pays off later.

Fix the randomness

The obvious step, and still the one most often forgotten. There's more than one random number generator in a typical ML stack, so I set them all in one place:

import random, numpy as np, torch

def set_seed(seed: int = 42):
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)

Even with seeds set, GPU runs can still differ slightly. I'm fine with that, as long as I know roughly how big the noise is. Running the same config with three different seeds tells you whether a 0.5% improvement is real or just luck.

Make the config a real object

Hyperparameters scattered across notebook cells are where reproducibility goes to die. I keep them in one dataclass and save it next to the results of every run:

from dataclasses import dataclass, asdict
import json

@dataclass
class Config:
    seed: int = 42
    lr: float = 3e-4
    batch_size: int = 64
    epochs: int = 20
    data_version: str = "v3"

cfg = Config(lr=1e-4)
json.dump(asdict(cfg), open(f"runs/{run_name}/config.json", "w"), indent=2)

Version the data, not just the code

Git tracks code, but most of my "why is this different?" moments came from the data changing underneath me. A re-exported CSV, a fixed label, a new filter upstream. At minimum I record a hash of the training file with each run. For bigger projects, a tool like DVC does this properly.

Record the environment

A pip freeze saved with each run is cheap and has saved me more than once, when a library update quietly changed a default.

What a run folder looks like for me

  • config.json: every setting used
  • git_commit.txt: the exact code version
  • data_hash.txt: which data it saw
  • requirements.txt: library versions
  • metrics.json: the results

With those five files I can explain any number I've reported, and that's really the point. A result you can't reproduce is just an anecdote.
