Why your validation score lies: data leakage

September 24, 2026    Suraj Nahak

Data LeakageValidationPitfalls

A validation score that's too good should worry you more than one that's too low. A bad score at least tells you something honest. A suspiciously high one usually means information from the test set has leaked into training somewhere, and the model is getting credit for an answer it already saw.

Here are the leaks I check for now, roughly in the order I've been bitten by them.

1. Preprocessing before the split

This is the classic one. You scale or impute the whole dataset, then split it. The mean and standard deviation you used were partly computed from the test rows, so the test set isn't really unseen anymore.

The fix is to put every preprocessing step inside a pipeline, so it's fit on the training fold only:

from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score

model = make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000))
scores = cross_val_score(model, X, y, cv=5)

2. The same person (or patient, or device) on both sides

If your data has several rows per user, a random split will happily put some of a user's rows in train and the rest in test. The model learns to recognise the user, not the pattern. Scores look great, then real users show up and it falls apart.

Use a grouped split, and add a quick test so it can't silently regress:

from sklearn.model_selection import GroupKFold

cv = GroupKFold(n_splits=5)
for train_idx, test_idx in cv.split(X, y, groups=df["user_id"]):
    overlap = set(df.user_id.iloc[train_idx]) & set(df.user_id.iloc[test_idx])
    assert not overlap

3. Features from the future

This is the hardest one to spot. A column like days_until_churn or final_status obviously knows the answer. But it's often subtler: a "last updated" timestamp that only changes after the event, or an aggregate computed over the whole history including dates after the prediction point.

My rule: for every feature, ask "would I actually have this value at the moment I need to make the prediction?" If the answer is "not quite", it goes.

4. Time series split randomly

If the data has a time order, shuffle-and-split lets the model train on Tuesday and get tested on Monday. Always split by time: train on the past, validate on what comes after.

A quick sanity check

When a score surprises me, I train a model to predict whether a row came from train or test. If it can tell them apart easily, something about the split is off. And if one feature is doing all the work in the real model, I look at that feature very closely before celebrating.

None of these leaks throw errors. That's the whole problem. You only catch them if you go looking.
