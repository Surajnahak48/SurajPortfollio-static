From notebook to service: packaging a model

September 06, 2026    Suraj Nahak

MLOpsDockerDeployment

Every ML project I've worked on hits the same point: the model works in the notebook, and someone asks "great, how do we use it?" The honest answer is usually "you'd have to run my notebook, in my environment, with the cells in the right order."

This post covers the minimum I do now to get from that point to a small service someone else can run. Nothing fancy, just the parts that tend to get skipped.

Get the logic out of the notebook

First, I move the preprocessing and prediction code into a plain Python module. The notebook is fine for exploring, but it hides state: a variable defined in a cell you deleted, or a cell that was run twice. A module run from a clean start can't hide anything.

The most important part is to save the preprocessing with the model. If the scaler or encoder lives in a separate step, sooner or later someone will use the wrong one.

import joblib
from sklearn.pipeline import make_pipeline

pipeline = make_pipeline(preprocessor, model)
pipeline.fit(X_train, y_train)
joblib.dump(pipeline, "model.joblib")

Wrap it in a tiny API

I usually reach for FastAPI because it validates the input for me. If a request is missing a field, the caller gets a clear error instead of a confusing stack trace from deep inside scikit-learn.

from fastapi import FastAPI
from pydantic import BaseModel
import joblib

app = FastAPI()
pipeline = joblib.load("model.joblib")  # load once at startup, not per request
MODEL_VERSION = "2026-09-01"

class Features(BaseModel):
    age: int
    plan: str
    monthly_usage: float

@app.post("/predict")
def predict(f: Features):
    row = [[f.age, f.plan, f.monthly_usage]]
    score = float(pipeline.predict_proba(row)[0, 1])
    return {"score": score, "model_version": MODEL_VERSION}

Returning the model version with every prediction seems minor, but it's the first thing you want when someone reports a strange result two months later.

Put it in a container

A Dockerfile pins the Python version and dependencies, so "works on my machine" becomes "works on any machine with Docker".

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "service:app", "--host", "0.0.0.0", "--port", "8000"]

Pin exact versions in requirements.txt, especially scikit-learn. A model pickled with one version is not guaranteed to load correctly in another.

A short checklist before calling it done

  • Can someone build and run it from the README alone?
  • Is there a /health endpoint for whatever runs the container?
  • Does one test send a real example through the API and check the response shape?
  • Are predictions logged somewhere, so you can monitor them later?

None of this is hard, but it's the difference between a model and a product. A model that people can actually call is usually more valuable than a slightly better one stuck in a notebook.
