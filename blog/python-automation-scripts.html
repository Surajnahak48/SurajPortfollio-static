Automating repetitive work with small Python tools

August 01, 2026    Suraj Nahak

AutomationPythonTools

Some of the code I'm happiest with isn't a model or a system. It's a 40-line script that renames files, or one that pulls a report every Monday so nobody has to do it by hand. They're not impressive, but they get used every week.

When is it worth automating?

My rough rule: if I've done the same manual task three times and expect to do it again, I write a script. The first time I'm still learning what the task actually is. By the third, I know the steps well enough to write them down, and writing them down in Python isn't much more work than writing them in a document.

The other signal is when a task is easy to get slightly wrong. Copying numbers between spreadsheets, renaming hundreds of files, cleaning the same columns every export. People make small mistakes on tedious work. Scripts don't get bored.

A shape that works for almost everything

Most of my small tools look like this: take a folder or file as input, process each item, print what changed. The one feature I always add is --dry-run, which shows what would happen without touching anything.

import argparse
from pathlib import Path

def main():
    parser = argparse.ArgumentParser(description="Tidy up exported report files.")
    parser.add_argument("folder", type=Path)
    parser.add_argument("--dry-run", action="store_true")
    args = parser.parse_args()

    for path in sorted(args.folder.glob("*.csv")):
        new_name = path.name.lower().replace(" ", "_")
        if new_name == path.name:
            continue
        print(f"{path.name}  ->  {new_name}")
        if not args.dry_run:
            path.rename(path.with_name(new_name))

if __name__ == "__main__":
    main()

The dry run is what makes me (and anyone else) actually trust the script. You run it once, read the output, and only then let it change things.

Things I've learned the hard way

  • Never overwrite the original. Write to a new folder, or keep a backup. Undo isn't free in a script.
  • Make it safe to run twice. If it crashes halfway, running it again should just finish the job, not double everything.
  • Print what you did. A silent script that "worked" is hard to trust.
  • Put a usage example at the top. In six months you won't remember the arguments.

Don't over-build it

It's tempting to turn a useful script into a proper tool with a config system, plugins and a GUI. Usually that's a mistake. The value was in it being small and quick to change. I only add structure when the script actually needs it, for example when other people start relying on it.

If there's a task you dread every week, it's probably a good candidate. Start with the dry run.
