Dynamic programming without the fear

September 15, 2026    Suraj Nahak

AlgorithmsDynamic ProgrammingPython

For a long time, dynamic programming was the topic I quietly hoped wouldn't come up. The solutions I read looked like magic: a 2D table, some indices, and a loop that somehow produced the answer. I could follow them, but I couldn't have written one.

What finally made it click was realising that almost nobody writes the table first. You write the slow, obvious recursive solution, and then you make it fast.

Step 1: write the brute force recursion

Take the classic coin change problem: what's the fewest coins that add up to an amount? Forget efficiency and just describe the choice. For any amount, I can use one coin of some value, then solve the smaller problem that's left.

def min_coins(amount, coins):
    if amount == 0:
        return 0
    if amount < 0:
        return float("inf")
    return 1 + min(min_coins(amount - c, coins) for c in coins)

This is correct, and it's painfully slow, because it solves the same sub-amounts over and over again.

Step 2: remember answers you've already computed

That repetition is the whole signal. If a function gets called with the same arguments many times, cache it. In Python that's a single line:

from functools import lru_cache

def min_coins(amount, coins):
    @lru_cache(maxsize=None)
    def solve(a):
        if a == 0:
            return 0
        if a < 0:
            return float("inf")
        return 1 + min(solve(a - c) for c in coins)

    result = solve(amount)
    return -1 if result == float("inf") else result

That's dynamic programming. Really. Each sub-amount is now solved once, so the running time drops from exponential to amount × len(coins).

Step 3 (optional): turn it into a table

If recursion depth becomes a problem, or you want to save memory, you can flip it around and fill the answers bottom-up, smallest amount first:

def min_coins(amount, coins):
    best = [0] + [float("inf")] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                best[a] = min(best[a], best[a - c] + 1)
    return -1 if best[amount] == float("inf") else best[amount]

Compare this with the memoized version and you'll see it's the same logic. best[a] is just solve(a) written down in advance. The tables that used to scare me were never the starting point. They're what's left after a couple of mechanical steps.

The two questions I ask now

  • What's the state? The smallest set of values that fully describes a sub-problem (here, just the remaining amount).
  • What's the choice? What decision do I make at each step, and how does it shrink the state?

If I can answer both, the recursion more or less writes itself, and the rest is caching.
